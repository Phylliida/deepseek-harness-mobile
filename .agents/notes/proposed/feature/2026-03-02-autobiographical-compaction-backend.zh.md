# Agent Note: Autobiographical compaction backend

Status: proposed

[English](2026-03-02-autobiographical-compaction-backend.md) | 中文

## Problem

长时间运行的会话最终会撞上固定的上下文窗口。harness 的现有答案是[压力压缩](../../implemented/feature/2026-06-18-compaction-capability-seam.md)：表层越过阈值时，用一段检查点替换一个范围，后续每个检查点再合并前一个。因此会话可以无限延续，但它最久远的历史只剩下一段不是由 agent 自己写下的文本，没有特定的视角，也没有考虑在提供方提示词 cache 下重写它要付出什么代价。

Anima Connectome 的 `@animalabs/context-manager` `AutobiographicalStrategy` 正是为这一缺口而存在。它把陈旧历史切分为区块，按规划出的分辨率把每个区块折叠为第一人称回忆，随着回忆累积再把它们合并到更粗的层级，并在每一轮针对 token 墙重新规划整个布局，其优化目标是提示词 cache 扰动，而不仅是 token 数量。

采用它需要回答本注记所要解决的四个问题：当第二份存储在其之上做规划时，会话的权威归谁；记忆引擎应以依赖形式引入还是以源码形式 vendor；当 seam 的摘要约定是 user 角色检查点时，回忆该如何搭载其上；以及人如何在不卸载后端的前提下让引擎停止形成记忆。

## Proposal

新增 `packages/compaction/compaction-autobiographical`，作为 `ctx.compaction` 的第二个 Service Provider，由 `AutobiographicalStrategy` 驱动；并新增 `packages/compaction/command-autobio`，作为对其自动折叠的用户控制。配置、模型可见约定与已知限制见[包 README](../../../../packages/compaction/compaction-autobiographical/README.md)；命令自身的约定见[其 README](../../../../packages/compaction/command-autobio/README.md)。

## 权威归属：策略负责规划，harness 负责落地

harness 会话日志始终是唯一权威。每个会话在 Chronicle 存储之上的一份 `ContextManager` 镜像该会话，使策略得以在其上做规划；而从 harness 这一侧看，镜像只是单向写入：以追加为来源的表层事件只回放一次，每条都盖上其日志 seq，替换节点——包括本后端自身的折叠——绝不会被回镜。回放水位从最新一条已镜像消息中恢复，因此重新打开会话是继续而不是重新摄取。

策略唯一的输出是一份布局。后端把该布局与实时表层做差异比对，并通过 seam 的带标记事务（`compaction/start`、每次折叠一条 `compaction/summary`、`compaction/end`）落地差异，因此折叠是一次有日志、有计量、可回放的表层变更，而不是另一份存储内部的私有编辑。

## 以依赖形式复用已发布的包，而不 vendor 源码

`@animalabs/context-manager` 与 `@animalabs/membrane` 保持为 npm 依赖，Chronicle 经由前者传递引入。`MembraneBridge` 把库的 `complete()` 适配到 `ctx.llm.stream()`，因此凭证、路由、重试与用量都留在 harness 适配器侧，只有请求组装属于我们。

vendor（即 [Cordis 的做法](../../../../vendor/README.md)）被否决。该库是 26k 行源码加一层 Rust N-API 存储；放在覆盖率门禁 `packages/*/*/src` include 范围之外 vendor，会形成一块没有任何度量覆盖的大型代码区域；放在包内 vendor，则会把外部源码拖入逐文件 100% 覆盖率要求，并带来长期审阅外部代码的负担。采用依赖可让更新路径缩短为一次版本升级，并把 harness 自有代码限定在镜像、applicator 与桥接层。

## 折叠节点是 assistant 回忆，而不是 seam 检查点

seam 对替换的约定是由 `compactCheckpointSource` 构建、并对模型框定为已建立背景的 `user/message`。回忆既不是背景，也不属于 user：它是 agent 自己的过去。因此它以 `assistant/message` 落地，文本以 `[Recall <id>]` 头开始；后续轮次也据此识别折叠节点并展开其覆盖范围。

这一代价被明确记录而非隐藏：按消息来源识别压缩检查点的消费方无法识别折叠节点，因此未来任何 seam 层面的检查点记账都必须学会这第二种形态，或者把折叠节点当作普通 assistant 消息处理。

## 依据渲染结果做规划，而不是依据策略内部结构

后端调用 `manager.compile(budget)` 解析布局，再调用 `previewContext(budget, undefined, { render: true })` 取得该布局实际会渲染的条目。规划以这些渲染条目与表层做对账，并为每个节点标注它覆盖的原始 seq，使覆盖范围在不同折叠层级之间仍可比较。若从其他来源推导规划，就等于在本包内重复实现解析器。

预算来自适配器上报的上下文窗口，并可由配置覆盖。即使采用最粗分辨率也无法容纳的前沿会抛出 `OverBudgetError`，后端记录并吸收它：表层保持原样，提供方自身的溢出恢复仍是最终权威。折叠同样不以 seam 的压力触发条件为前提——当策略对该区间给出的分辨率要求折叠时就折叠，这正是调度得以持续而非被动的原因。

## 声音完整性约束记忆形成路由

记忆承载身份，因此策略会接收到会话自身已路由的模型作为其 `compressionModel`，并拒绝以替代声音形成记忆。这里刻意不提供可配置的摘要路由：自传式记忆是 agent 在书写自己的历史，因此记忆形成始终跟随会话最近一次已路由请求（回退到 agent 自身目标）；无法解析路由的会话不折叠任何内容，而不是交给另一个模型。压缩调用携带 `purpose: 'compaction'`。

## 折叠形态：每个区间一个节点，细化被钳制

一次折叠用恰好一个节点遮蔽一个区间，规划也从不让某个区间的节点数增长。这一形态使每次折叠都能表达为 seam 既有的替换操作，对变粗而言也足够——而变粗正是会话增长时的方向。

它同时也是本后端核心限制的来源。比表层已显示的更细的规划分辨率无法落地，因为一个节点无法重新拆成多个，于是较粗的回忆继续保留。归档保留每个层级，原始日志记录也从未删除，但表层在每个区间上是单调的：已折叠区间不会回到原始形态。展开需要 seam 目前不具备的表层能力，因此 `compactRegion` 未实现，并选择拒绝而不是假装支持。

## 折叠资格取决于会话的工具 schema

对于包含工具块的区块，该库会拒绝压缩，直到宿主声明了该 agent 的工具定义为止，因为对工具对话做一次不含工具的重新回放会触发提供方的拒答分类器。因此后端每轮都会把会话已组装的 schema 推入归档。没有这一步，后端在纯文本会话上看起来一切正常，却永远不会折叠那些最需要折叠的工具密集型会话——这种失败是静默推迟，而不是报错。

这些声明就是实时请求所携带的 schema，被映射进库自身的类型。压缩调用本身仍不在链路上声明任何工具：压缩路径无法继续一次工具调用作答，而该库自身的重试策略假定摘要模型可能按既有模式作答，因此声明它们只会招来一个该路径必须拒绝的回复。

## 运行时开关切换的是自动折叠，而不是引擎

`setAutomaticFolding(false)` 会移除由 `auto` 配置项注册的步骤边界监听器；`isAutomaticFoldingEnabled` 报告状态，而 `packages/compaction/command-autobio` 中的 `/autobio` 是它面向用户的入口。选择移除监听器而不是在监听器内部做判断，是为了让“关闭”只有一种含义：以 `auto: false` 构造的后端与在运行时被关闭的后端是同一个后端，在步骤边界上完全不存在。

被切换的只是引擎自身的调度。显式折叠仍然可用——`/compact` 以及任何其他 `compactNow()` 调用方仍会折叠——因为该开关回答的是“agent 是否应当自行改写自己的历史”，而不是“这个会话是否还能再折叠”。开关落地时已在执行中的折叠仍会完成，包括已经在运行的记忆形成调用。

该命令与具体后端绑定，并明确说明这一点：它把 `ctx.compaction` 收窄为 `AutobiographicalCompactionEngine`，对其他任何提供方都报错，因为压缩是一个拥有多个提供方的 seam，而一个在它并不驱动的后端上静默无操作的控制入口，比一个明确拒绝的入口更糟。两个后果被明确写出而非隐藏：状态只存在于运行时（重启回到配置的 `auto`，日志也不记录折叠停止的原因），且它覆盖整个上下文，因为一个引擎服务于该上下文中的所有会话。

## Alternatives considered

- **把 `ContextManager` 作为拥有会话的旁路服务运行。** 否决：harness 会保留自己的日志与表层，而由第二份存储决定模型看到什么，于是遮蔽、投影、修复、工具配对与 transcript 派生都需要一套并行实现，两个权威还得在排序与恢复上长期保持一致。
- **vendor Anima 源码。** 因上述覆盖率门禁与审阅理由否决；此外，被 fork 的记忆引擎还需要人工与库变更保持同步。
- **不镜像日志，直接驱动策略。** 否决：该库是持续且在后台压缩的，因此无镜像的设计只能按需回灌历史，既失去 tick 调度，也失去“当时视角”——正是它让回忆成为某一时刻的证词，而非事后追述。
- **复用 `compaction-basic` 受保护的 `summarize()` 钩子。** 否决：该钩子按需为一个范围产出一份摘要，无法表达层级、按区间分辨率或 cache 感知的调度——而这些正是值得引入的部分。
- **产出 seam 的 `user/message` 检查点。** 否决：那会把 agent 自己的回忆呈现为 user 文本或已建立背景，与该设计所依赖的声音相矛盾。其识别代价改以上文记录。
- **把一个区间折叠为多个节点。** 暂缓，等待目前并不存在的表层能力：它能让区间在不展开的前提下细化，也是钳制细化这一限制最终应当修复的位置。
- **以 seam 的 `pressure`／`context-overflow` 触发条件作为折叠门槛。** 否决：该库自己的设计记录把“按数量或按危机”触发列为它要取代的失效模式，因为它会把深度重折叠推迟到罕见且代价最高的时刻。

## Acceptance criteria

- 超出窗口的会话继续服务请求时，逐字保留的近期尾部未被折叠，陈旧区间被 `[Recall <id>]` assistant 回忆替换，且每个原始事件仍留在日志中。
- 每次折叠都体现为同一个 `compactionId` 下的 `compaction/start` … `compaction/summary` … `compaction/end`，且 `CompactionResult` 报告实际落地的已遮蔽 seq 与 token 估算。
- 回忆正文由会话自身已路由的模型书写；无法解析路由的会话不折叠任何内容并发出警告。
- 在已有存储上重新打开会话时，从水位继续而不是重新镜像历史；`agent/disposed` 关闭存储，使下一个打开者不会被锁住。
- 规划失败、上下文窗口未知以及超出预算的前沿，都让该轮的表层保持逐字节不变。
- `compactNow()` 可按需折叠，`compactRegion()` 以 `ManualCompactionError('summary')` 拒绝。
- 历史中包含工具块的会话，在其已组装的工具 schema 进入归档后即可折叠。
- 自动折叠可在运行时开关而无需卸载后端：关闭期间步骤之间不落地任何折叠，显式调用仍会折叠，且命令会报告切换后所处的状态。
- 本包的测试钉住以下行为：折叠为 assistant 回忆节点、逐字尾部得以保留、区间请求被拒绝、引擎重启后的存储续用、工具 schema 推送，以及开关的两个方向。

## Risks

- 钳制细化是一个可见的保真度上限：区间在折叠状态下只能变粗，因此预算先缩小后增大的会话无法恢复此前丢失的细节。在表层能表达多节点折叠之前，`recentWindowTokens` 是让区间保持原始形态的唯一调节杆。
- 折叠节点是 assistant 消息，因此假设压缩总是留下 user 检查点的客户端、门禁或迁移会错误处理它们。
- 镜像是 `storeRoot` 下按会话划分的第二份持久产物，不受会话日志所拥有的保留或备份策略覆盖；丢失它会丢弃已形成的记忆，即使日志完好无损。
- 该库是快速演进的外部依赖，其提示词与默认值都是模型可见的，因此一次版本升级就可能改变模型读到什么，而本仓库没有任何改动。
- 记忆形成是每个区块一次真实推理。大量积压会在后台支付这项成本，因此缓慢的记忆形成或并发设置表现为折叠滞后，而不是轮次失败。
- `kv-stable` 策略是以 Anthropic 的提示词 cache 经济性为基准校准的。该策略在结构上是 cache 感知的，但其常量并未针对本 harness 的提供方调校。
- 会话可能在折叠被关闭期间持续增长，而这正是本后端存在所要避免的状态：表层停止变粗，下一轮折叠要付出更大代价。因此该开关是诊断与成本控制手段，而不是一种可以长期保持的模式。
- 工具 schema 每轮推送且只保留最新一份，因此对在另一套工具集下记录的对话所做的折叠，是依据当前工具集压缩的——这是库自身单槽位的约定，并非 harness 的疏漏。
