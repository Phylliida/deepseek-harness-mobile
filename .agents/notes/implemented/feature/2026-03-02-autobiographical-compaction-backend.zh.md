# Agent Note: Autobiographical compaction backend

Status: implemented

[English](2026-03-02-autobiographical-compaction-backend.md) | 中文

## Problem

长时间运行的会话最终会撞上固定的上下文窗口。harness 的现有答案是[压力压缩](../../implemented/feature/2026-06-18-compaction-capability-seam.md)：表层越过阈值时，用一段检查点替换一个范围，后续每个检查点再合并前一个。因此会话可以无限延续，但它最久远的历史只剩下一段不是由 agent 自己写下的文本，没有特定的视角，也没有考虑在提供方提示词 cache 下重写它要付出什么代价。

Anima Connectome 的 `@animalabs/context-manager` `AutobiographicalStrategy` 正是为这一缺口而存在。它把陈旧历史切分为区块，按规划出的分辨率把每个区块折叠为第一人称回忆，随着回忆累积再把它们合并到更粗的层级，并在每一轮针对 token 墙重新规划整个布局，其优化目标是提示词 cache 扰动，而不仅是 token 数量。

采用它需要回答本注记所要解决的四个问题：当第二份存储在其之上做规划时，会话的权威归谁；记忆引擎应以依赖形式引入还是以源码形式 vendor；当 seam 的摘要约定是 user 角色检查点时，回忆该如何搭载其上；以及人如何在不卸载后端的前提下让引擎停止形成记忆。

## Decision

`packages/compaction/compaction-autobiographical` 是 `ctx.compaction` 的第二个 Service Provider，由 `AutobiographicalStrategy` 驱动。配置、模型可见约定与已知限制见[包 README](../../../../packages/compaction/compaction-autobiographical/README.md)。

## 权威归属：策略负责规划，harness 负责落地

harness 会话日志始终是唯一权威。每个会话一份 `ContextManager`，运行在一个替代库的 `JsStore` 的内存存储之上，而折叠是它唯一的写入。没有其他东西喂给它：该存储与运行时切片同寿，因此每个会话不存在第二份持久产物，也没有可供恢复的水位。

因此打开会话是重建而非续用。以追加为来源的表层事件只回放一次，每条都盖上其日志 seq；回忆则从日志本就持有的两处重建——`autobio/memory` 事件携带其正文、层级与被覆盖的 seq 范围，而替换其区间的 `assistant/message` 在同一个 `compactionId`（`autobio:<summaryId>`）下携带同样的文本，指明它所代表的回忆。替换节点绝不会被镜像，因为规划器会发现某个折叠节点所覆盖的地面已被占用，于是不要求在那里折叠。

策略唯一的输出是一份布局。后端把该布局与实时表层做差异比对，并通过 seam 的带标记事务（`compaction/start`、每次折叠一条 `compaction/summary`、`compaction/end`）落地差异，因此折叠是一次有日志、有计量、可回放的表层变更，而不是另一份存储内部的私有编辑。

## 以依赖形式复用已发布的包，而不 vendor 源码

`@animalabs/context-manager` 与 `@animalabs/membrane` 是 npm 依赖。`MembraneBridge` 把库的 `complete()` 适配到 `ctx.llm.stream()`，因此凭证、路由、重试与用量都留在 harness 适配器侧，只有请求组装属于我们。无论是否这样做，membrane 都在依赖图上，因为该库以值的形式导入了原生格式化器。

vendor（即 [Cordis 的做法](../../../../vendor/README.md)）被否决。该库是 26k 行源码加一层 Rust N-API 存储；放在覆盖率门禁 `packages/*/*/src` include 范围之外 vendor，会形成一块没有任何度量覆盖的大型代码区域；放在包内 vendor，则会把外部源码拖入逐文件 100% 覆盖率要求，并带来长期审阅外部代码的负担。采用依赖可让更新路径缩短为一次版本升级，并把 harness 自有代码限定在存储适配层、规划器与桥接层。

## 折叠节点是 assistant 回忆，而不是 seam 检查点

seam 对替换的约定是由 `compactCheckpointSource` 构建、并对模型框定为已建立背景的 `user/message`。回忆既不是背景，也不属于 user：它是 agent 自己的过去。因此它以 `assistant/message` 落地，其 `compactionId` 同时是库的折叠标识与 seam 事务的标识，于是后续轮次仅凭来源即可识别折叠节点，无需再从散文里解析回来。

其文本仍以 `[Recall <id>]` 头开始，这既是 `compactionId` 之前的折叠所采用的约定，也是回放读取它们的回退路径。两者同时存在时以来源 id 为准，头部严格只是回退。

这一代价被明确记录而非隐藏：按消息来源识别压缩检查点的消费方无法识别折叠节点，因此未来任何 seam 层面的检查点记账都必须学会这第二种形态，或者把折叠节点当作普通 assistant 消息处理。

## 依据策略上报的内容做规划，而不是再造一个解析器

后端调用 `manager.compile(budget)` 解析布局，随后依据策略自述其持有的条目做规划。规划按回忆划分表层，并为每个节点标注它覆盖的原始 seq，把折叠节点展开为它所代表的事件，使覆盖范围在不同折叠层级之间仍可比较。策略逐字保留的区间读自它自身的近期窗口起点；若从其他来源推导其中任何一项，就等于在本包内重复实现解析器。

预算来自适配器上报的上下文窗口，并可由配置覆盖、由 `operatingWindowTokens` 封顶。即使采用最粗分辨率也无法容纳的前沿会抛出 `OverBudgetError`，后端会按实测下限重试一次，否则吸收它：表层保持原样，提供方自身的溢出恢复仍是最终权威。折叠同样不以 seam 的压力触发条件为前提——当策略对该区间给出的分辨率要求折叠时就折叠，这正是调度得以持续而非被动的原因。

## 声音完整性约束记忆形成路由

记忆承载身份，因此策略会接收到会话自身已路由的模型作为其 `compressionModel`，并拒绝以替代声音形成记忆。这里刻意不提供可配置的摘要路由：自传式记忆是 agent 在书写自己的历史，因此记忆形成始终跟随会话最近一次已路由请求；无法解析路由的会话不折叠任何内容，而不是交给另一个模型。压缩调用携带 `purpose: 'compaction'`。

## 折叠形态：每个区间一个节点，细化被钳制

一次折叠用恰好一个节点遮蔽一个区间，规划也从不让某个区间的节点数增长。这一形态使每次折叠都能表达为 seam 既有的替换操作，对变粗而言也足够——而变粗正是会话增长时的方向。

它同时也是本后端核心限制的来源。比表层已显示的更细的规划分辨率无法落地，因为一个节点无法重新拆成多个，于是较粗的回忆继续保留。每个层级都留在日志中，原始记录也从未删除，但表层在每个区间上是单调的：已折叠区间不会回到原始形态。展开需要 seam 目前不具备的表层能力，因此 `compactRegion()` 以 `ManualCompactionError('summary')` 拒绝，而不是假装支持。

## 折叠资格取决于会话的工具 schema

对于包含工具块的区块，该库会拒绝压缩，直到宿主声明了该 agent 的工具定义为止，因为对工具对话做一次不含工具的重新回放会触发提供方的拒答分类器。因此后端每轮都会把实时请求所携带的 schema 推入上下文，并映射进库自身的类型。没有这一步，后端在纯文本会话上看起来一切正常，却永远不会折叠那些最需要折叠的工具密集型会话——这种失败是静默推迟，而不是报错。

压缩调用本身仍不在链路上声明任何工具：压缩路径无法继续一次工具调用作答，而该库自身的重试策略假定摘要模型可能按既有模式作答，因此声明它们只会招来一个该路径必须拒绝的回复。

## 自动折叠是加载期设置

`auto`（默认 `true`）在加载时决定是否注册步骤边界监听器，而构造函数是唯一读取它的地方。无论该设置如何，显式折叠始终可用：`compactNow()` 忽略 seam 的触发条件并按需折叠，`/compact` 可抵达它。

不存在运行时开关，也不存在状态访问器。关闭折叠是一次配置变更加一次重载；被留在 `auto: false` 的会话只在有东西调用 `compactNow()` 时才折叠。

## Alternatives considered

- **把 `ContextManager` 作为拥有会话的旁路服务运行。** 否决：harness 会保留自己的日志与表层，而由第二份存储决定模型看到什么，于是遮蔽、投影、修复、工具配对与 transcript 派生都需要一套并行实现，两个权威还得在排序与恢复上长期保持一致。
- **在日志之外保留一份持久存储。** 否决：那是每个会话的第二份产物，不受日志所拥有的保留策略覆盖，丢失它会丢弃已形成的记忆，而日志却完好无损——而要留住它就需要水位、镜像以及两者之间的对账，而这些正是回放根本不需要的东西。
- **vendor Anima 源码。** 因上述覆盖率门禁与审阅理由否决；此外，被 fork 的记忆引擎还需要人工与库变更保持同步。
- **不回放日志，直接驱动策略。** 否决：该库是持续且在后台压缩的，因此不回放的设计只能按需回灌历史，既失去 tick 调度，也失去“当时视角”——正是它让回忆成为某一时刻的证词，而非事后追述。
- **复用 `compaction-basic` 受保护的 `summarize()` 钩子。** 否决：该钩子按需为一个范围产出一份摘要，无法表达层级、按区间分辨率或 cache 感知的调度——而这些正是值得引入的部分。
- **产出 seam 的 `user/message` 检查点。** 否决：那会把 agent 自己的回忆呈现为 user 文本或已建立背景，与该设计所依赖的声音相矛盾。其识别代价改以上文记录。
- **把一个区间折叠为多个节点。** 暂缓，等待目前并不存在的表层能力：它能让区间在不展开的前提下细化，也是钳制细化这一限制最终应当修复的位置。
- **以 seam 的 `pressure`／`context-overflow` 触发条件作为折叠门槛。** 否决：该库自己的设计记录把“按数量或按危机”触发列为它要取代的失效模式，因为它会把深度重折叠推迟到罕见且代价最高的时刻。

## Consequences

这一取舍换来的是一个任何东西都只有一份持久副本的设计。超出窗口的会话继续服务请求时，逐字保留的近期尾部未被折叠，陈旧区间被 `[Recall <id>]` assistant 回忆替换，且每个原始事件仍留在日志中；重新打开会话是回放该日志，而不是与第二份存储对账，且上一轮运行形成的折叠不会被重新形成，因为规划器发现它们覆盖的地面已被占用。每次折叠都体现为同一个 `compactionId` 下的 `compaction/start` … `compaction/summary` … `compaction/end`，且 `CompactionResult` 报告实际落地的已遮蔽 seq 与 token 估算。规划失败、上下文窗口未知以及超出预算的前沿，都让该轮的表层保持逐字节不变，而 `compactRegion()` 以 `ManualCompactionError('summary')` 拒绝。

代价是运行时开关。在不卸载后端的前提下于运行时停止记忆形成、再把它打开，这曾是一项真实能力，而它没有了：它面向用户的入口、两个访问器，以及承载两者的命令包都被删除而不是维护，因为这整套入口只回答一个加载期布尔值。已在运行的会话会持续折叠，直到被重新配置并重载，而日志也不记录折叠停止的原因。

代价还包括每次打开都要回放。长会话会重读自己的历史来重建金字塔，这是持久存储在水位处做过一次的工作；日志本就是会话已经打开的读取，因此这份代价付在时间上，而不是付在正确性上。

- 钳制细化是一个可见的保真度上限：区间在折叠状态下只能变粗，因此预算先缩小后增大的会话无法恢复此前丢失的细节。在表层能表达多节点折叠之前，`recentWindowTokens` 是让区间保持原始形态的唯一调节杆。
- 折叠节点是 assistant 消息，因此假设压缩总是留下 user 检查点的客户端、门禁或迁移会错误处理它们。
- 该库是快速演进的外部依赖，其提示词与默认值都是模型可见的，因此一次版本升级就可能改变模型读到什么，而本仓库没有任何改动。
- 记忆形成是每个区块一次真实推理。大量积压会在后台支付这项成本，因此路由或并发配置不当表现为折叠缓慢，而不是轮次失败。
- `kv-stable` 策略是以 Anthropic 的提示词 cache 经济性为基准校准的。该策略在结构上是 cache 感知的，但其常量并未针对本 harness 的提供方调校。
- 会话可能在折叠被关闭期间持续增长，而这正是本后端存在所要避免的状态：表层停止变粗，下一轮折叠要付出更大代价。
- 工具 schema 每轮推送且只保留最新一份，因此对在另一套工具集下记录的对话所做的折叠，是依据当前工具集压缩的——这是库自身单槽位的约定，并非 harness 的疏漏。
