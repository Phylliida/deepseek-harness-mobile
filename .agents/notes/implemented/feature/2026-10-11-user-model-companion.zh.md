# Agent Note: User-model companion

Status: implemented

[English](2026-10-11-user-model-companion.md) | 中文

## Problem

通过 GUI 使用编程智能体时，有三类反复出现的交互离不开人类在场：智能体停滞空闲时的回复、回答它的结构化提问、裁决它的工具审批请求。因此长时间运行的目标无法无人值守，也无法演练或自动化对话中用户一侧的行为。goal-round 驱动器已经解决了目标的停滞续行问题，但它驱动的是*智能体*，用的是固定提示词；没有任何组件扮演*用户*——根据转录决定说什么、按提问作答、裁决审批、并在目标达成时停下。

设计问题在于第二个参与者的权威状态放在哪里。进程内持有会在重启时丢失启用状态，并可能在驱动器、交互接缝与 GUI 之间产生分歧。另建持久会话或分叉对话则会破坏单一转录的心智模型，而本特性正是迈向多智能体聊天的踏脚石。

## Decision

模型用户伴随：第二个可选模型，按会话启用，携带人类书写的目标提示词，在同一会话中扮演用户角色。三层落地：

- **域 —— `@deepseek-ai/dsh-user-model`。** 启用事实是持久的会话事件对：`user-model/armed { provider, model, prompt }` 与 `user-model/disarmed { reason }`，由 `readUserModelSelection` 反向折叠。每个消费者——驱动器、apiproxy 转发、`userModel` 会话投影、冷恢复——都只读日志；不存在会产生分歧的进程内权威。每次辅助生成都经过 `callUserModel`：在派发前把确切请求追加为 log-only 的 `user-model/request` 事件（模型可见 ⟺ 已记录，与 session-title-llm 的派发前记录一致）。该包还持有人设系统提示词、角色翻转的转录构建器，以及问题／审批的提示词渲染器与解析器。
- **驱动器 —— `@deepseek-ai/dsh-user-model-driver`。** 在 `agent/status` 转为 idle、任务集合变化、`user-model/armed` 事件时唤醒；仅当 fiber 处于 ACTIVE、该 `Agent` 生命周期已注册、智能体空闲且收件箱为空、无运行中的所属任务时才驾驭。每次等待中的生成返回后重新检查就绪条件，因此生成期间到来的人类输入使回复失效，而非被打断。`maxReplies`（默认 20）限制每次启用的回复条数；`maxTokens`（默认 4096）限制每次生成。停用原因：`user`、`complete`（`<task-complete/>` 哨兵，必须位于回复末尾；其前文本作为收尾反馈送达）、`turn-failed`、`generation-failed`、`replies-exhausted`。停用追加本身失败时失败即关闭：不再回复，并记录日志。`Session.append` 拒绝在事件发布期间重入，因此 armed 事件的唤醒经 microtask 调度，调度期间观察到的停用会被记录并由该次运行提交。
- **交互接缝 —— apiproxy。** `session.selectUserModel` 经 `ctx.llm.resolveCallConfig` 校验路由并追加 armed/disarmed 事件。启用期间，问题提供者与审批监听器优先咨询用户模型：问题由解析出的选项列表回答，审批由附确切调用参数渲染后解析出的 `{"approved": ...}` 裁决回答。辅助调用的任何失败都回退到原有的人类 mux 路径，因此启用用户模型绝不会让问题或审批悬空。`userModelMaxTokens`（默认 4096）约束这些调用。

用户模型的回复以 `user/message` 事件进入会话，其来源是声明合并出的 `user-model` 种类（`{ kind: 'user-model', provider, model }`），绝不使用普通的 `user` 种类：标题生成与技能扫描仍然只看到人类键入的消息，回复上限也只统计当前启用下模型来源的回复。

GUI 在模型 seat 中获得第三个触发器（`packages/client/ui-model-selection`）：目标编辑框在填写非空目标后启用目录行；启用期间显示已启用摘要与停用行。该 seat 回显 `userModel` 投影而非目录状态，因此驱动器或其他客户端提交的停用就是 seat 下一次显示的内容。

## Alternatives considered

- **进程内启用持有（按会话 id 键控的注册表）。** 否决：重启与冷恢复会静默丢失启用状态，且驱动器、接缝、投影各自需要这个可变内存事实的视图。持久事件对让回放成为唯一权威，无需额外机制——折叠只是一次反向扫描。
- **回复伪装成 `source: { kind: 'user' }`。** 否决：标题生成与技能扫描把 `user` 消息视为人类键入；模型撰写的回复会渗入仅限人类的启发式。专用来源种类让每个仅限人类的消费者在构造上保持正确，同时消息对智能体仍读作 user 角色。
- **为用户模型的视角另建会话或分叉转录。** 否决：本特性是迈向单一转录内多智能体聊天的踏脚石；平行会话会重复历史、加倍持久存储，并为角色翻转构建器一次推导即可得到的东西发明同步协议。
- **给 `GenerateOptions.purpose` 扩展 `user-model` 变体。** 否认为不必要：用途记录在 log-only 的 `user-model/request` 事件上，它携带的上下文（系统提示词、消息、路由）比 LLM 流上的用途标签更多，且闭合的用途联合保持不变。
- **类似 goal-round 驱动器的 pre-step 预留栅栏。** 否决：goal 驱动器需要 CAS 预留，因为 `roundsStarted` 是必须每轮恰好推进一次的持久计数器。用户模型驱动器没有需要保护的持久计数器——其上限折叠容忍偶发的回复丢弃，生成后的就绪复查已经阻止了失效发送。

## Consequences

无人值守的会话可以运行到模型判定的完成：智能体的停滞、提问与审批请求都由启用的模型回答，人类事后阅读转录，每次辅助调用都逐字记录在会话日志上。`userModel` 投影让 GUI（及未来的客户端）无需改动 wire 协议即可获得启用状态。

代价：启用的会话在两个模型上消耗 token；回复上限是条数而非资源预算，失控循环只受 `maxReplies`（每次启用 20 条）约束；完成判定是用户模型自己的，没有独立评估器；问题与审批的回答质量完全取决于启用的模型——弱路由回答得也弱，人类只能在日志中看到结果。每个会话一个用户模型；本特性作为踏脚石所指向的多智能体面板仍是暂缓事项。
