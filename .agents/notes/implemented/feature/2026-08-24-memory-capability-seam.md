# Agent Note: Memory capability seam (OptMem design)

Status: implemented

English | [中文](2026-08-24-memory-capability-seam.zh.md)

## Problem

Agents have no permanent memory: everything they learn dies with the session, the compaction, or the vendor change. The harness's answer so far — workspace files, Agent Notes, skills — encodes how to work but not what was decided, tried, or learned about the user. [OptMem](https://github.com/VictorTaelin/OptMem) proved a minimal design that works: a 426-token prompt plus one dependency-free script over an append-only log, with measured continuity wins in multi-session coding workloads. The ask was that design as a first-class harness capability.

## Decision

**A capability seam, not a pasted prompt.** `packages/memory/` holds three packages: `dsh-memory` (the abstract `MemoryService` on `ctx.memory`), `dsh-memory-log` (the provider), and `dsh-tool-memory` (the Consumer: one `memory` tool plus the `tool:memory` prompt section). Mounting is opt-in per composition; the shipped bundles and presets are untouched.

**One provider, one global store, N project stores.** The provider wraps the grammar with two routing commands: `projects` lists the immediate child directories of `projectsRoot` (default: the process working directory, marked with which holds a store and which is active), and `use <name>` switches the active store into the `projectsDir` inside that directory (default `.memory/`, created on first selection); `use global` switches back. Every grammar command then runs against the active store, so the OptMem dialogue inside each store is byte-for-byte identical. Selection is process-wide in-memory state: all sessions in one composition share it, and an app restart returns to the global memory. The prompt section adds a store-first discipline — project facts belong in the selected project's memory, user-wide facts in the global one.

**The seam contract is the OptMem interface, verbatim.** `MemoryService.run(command: string): Promise<string>` takes one command string in OptMem's grammar (`wake [part [T]]`, `note "..."`, `nap [lo-hi "..."]`, `recall <regex>`, `zoom <lo-hi>`, `forget <lo-hi>`, `import <file>`) and returns the exact dialogue text upstream prints, `Run:` instructions included. One tool Consumer with one `command` parameter then works over any provider, the printed instructions are always copy-pasteable as the next call, and there is no parallel structured API to keep in sync with the text. Two upstream commands are deliberately absent: `init` (the provider creates its store at load from Config) and `config` (cordis.yml owns the sizes).

**Compression is agent-in-the-loop.** The provider never summarizes by itself; a due block surfaces as a nap request riding the note or wake result text — raw sources quoted, the answering `Run: nap a-b "<your line>"` line printed verbatim — and the model answers with that exact command string. This keeps memory quality on the model that understands the work, costs no background LLM calls, and makes every summary replayable from the session log (the request and the answer are ordinary tool results).

**Byte-compatible clean-room reimplementation, not vendoring.** The upstream repository carries no LICENSE file, so `dsh-memory-log` reproduces the algorithms and formats — fixed-width records (position is identity, O(1) seeks), the aligned power-of-two merge tree, age-decaying `cover()` tiling, torn-record repair, dense-prefix level files, local-date note stamps — without copying code. Record widths and limits follow upstream's measured values (320/288 bytes, 280-byte entries, RAW_MAX 16). Byte compatibility is pinned by `tests/fixtures/optmem-store/`, a store generated by the upstream Python tool and read back by the TypeScript port (both directions verified during development).

**The prompt is tuned, not pasted.** Upstream's generated prompt tells the agent to note "a task worth real effort", which in practice logs transient PR/CI status (upstream issue #14: 97.6% of note bodies held transient markers). `MEMORY_PROMPT` instead names what is durable — preferences, decisions with rationale, root causes, authorization boundaries — and explicitly excludes SHAs, CI results, and blockers, which the session log already records.

**Cross-process safety uses the house writer lock.** Node has no flock, so mutations serialize through `dsh-atomic-write`'s `withFileLock` on `LOG.txt` (a `wx`-created `LOG.txt.lock` sibling), one lock for the whole store like upstream's. The lock is deliberately NOT upstream's `.lock` file: flock and lockfiles cannot mutually exclude, and colliding on the name would instead deadlock every append against a store the Python tool ever touched. Sharing one store across the two implementations is a sequential affair; concurrent cross-implementation writers are unexcluded and unsupported.

## Alternatives considered

**Paste the OptMem prompt block into AGENTS.md and shell out to the Python script.** Rejected: no typed interface, no render intent, no coverage gates, and a Python runtime assumption that the mobile (Termux) composition does not carry. It also leaves the tool invisible to the catalog and doc gates.

**A thin Consumer wrapping the `memo` CLI.** Rejected: keeps the Python dependency and the unlicensed upstream artifact in the execution path, and shells out per operation through the bash tool's sandbox for what are single file seeks.

**Third-party MCP memory bridges.** `examples/mcp-memory/` already bridges Memorix, the MCP Reference Memory server, and Engram ([note](2026-07-31-third-party-memory-mcp-examples.md)) — all default-off, all vector/knowledge-graph stores with external servers. Rejected for this need: they trade a five-file local store for a network service, and their retrieval is embedding-similarity rather than the auditable, replayable summary tree this seam guarantees.

**A plural provider registry (`ctx.memories`, skill-shaped).** Rejected: one store is one identity; two mounted memory providers would fork the agent's past. No current consumer needs provider fan-out, and the singular abstract-service shape (compaction precedent) matches that. Store scoping lands inside the single provider instead: one service, one active store, agent-selected via routing commands — no second service name (`project-memory`) and no second tool was created, because the seam's `run(command)` contract already carries any command string and routing needs nothing else.

**Six typed tools (`memory_wake`, `memory_note`, …) or one tool with a structured `op` union.** Rejected in favor of maximal CLI fidelity: a single `memory` tool whose `command` string carries the OptMem grammar. Typed per-command schemas would buy arg validation but fork the interface the prompt teaches from the interface results print, and every `Run:` line would need translation instead of being sent verbatim. The quoting grammar (double quotes, with `\"` and `\\` escapes) is small and taught by example in the tool schema.

**Session events for memory state.** Rejected: memory is machine-scoped and outlives sessions by design; tool calls and results are logged centrally, so the model-visible⟺logged invariant holds without a `memory/*` event family.

## Consequences

The agent's memory costs a fixed prompt section plus wake pages (≤ wakeLines lines each, default 96 ≈ 8k tokens) per session start, and one note/nap exchange per durable fact. The seam adds no events, so projections, session-query, and persistence are untouched. Recall is regex-only — semantic search would need a different provider behind the same contract. Subagent exclusion and wake-first discipline are prompt-level, not enforced; a misbehaving composition can skip wake and the store simply stays unread. The store grows unboundedly by design (append-only; compression caps the read budget, not the storage). Store selection races are possible between parallel sessions sharing the composition and are acceptable for single-user deployments; the `projects`/`projectsDir` defaults (process cwd, `.memory`) put project memory in plain sight of the workspace rather than hidden in `$DSH_HOME`, which means a project store travels with the project directory it describes.
